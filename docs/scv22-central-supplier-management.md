# SC-V2.2 central supplier database contracts — review draft

Status: uninstalled source review artifacts only. No database connection, migration installation or SQL behavioral execution is performed in this phase. Do not run the SQL test against a hosted database. The shared SC-V2.1 contracts now include retained draft relationships, a safe display projection, and a validated country RPC envelope; application UI and Platform Admin writers are unchanged.

## Public RPCs

All are in `public`; only `authenticated` receives EXECUTE. Company UUID is explicit but never trusted without owner/active owner-or-manager membership verification. Staff management reads are deliberately denied; the existing narrow product discovery RPC remains unchanged.

- `subscriber_supplier_directory(p_company_account_id uuid, p_mode text = 'international', p_search text = '', p_limit integer = 50, p_offset integer = 0) RETURNS SETOF jsonb`
  - Exact fields: `kind: 'central'`, `id`, safely projected `name`, `status: 'active'`, `countries: string[] | null`.
  - Independent of enablement and product population. Literal case-insensitive substring search, not SQL wildcard search. Search <=100 characters; limit 1–100; offset 0–10000; deterministic name/UUID order. No total count is exposed. Offset pages can shift under concurrent catalogue edits; consumers refresh rather than treating pages as immutable snapshots.
  - `recommended` matches the explicitly saved operating country and fully valid supplier coverage. Missing country gives zero recommendations. `international` includes all active suppliers, including unknown coverage, regardless of country. It does not mean only foreign suppliers.
- `company_central_suppliers(p_company_account_id uuid, p_limit integer = 50, p_offset integer = 0) RETURNS SETOF jsonb`
  - Exact fields: `companyAccountId`, nested `supplier` with the directory fields (status also `paused`/`retired`/`draft`), `enabled`, `revision`, `availability`, `canEnable`.
  - Includes disabled and paused/retired/draft relationships. Configured enabled draft rows report `supplier-draft`; disabled rows report `disabled`, with `canEnable: false` for every non-active central supplier. Drafts are never in the pre-enable directory; only an existing draft relationship can be disabled, with identity/status retained. No private relationship metadata is returned. Eligibility never grants pricing or asset rights.
- `set_company_central_suppliers(p_company_account_id uuid, p_commands jsonb) RETURNS SETOF jsonb`
  - Commands are exact SC-V2.1 objects: `action: 'set-enabled'`, `companyAccountId`, `supplier: {kind: 'central', id}`, boolean `enabled`, nullable integer `expectedRevision`.
  - One command is the single-supplier interface. Maximum 100 commands and 64 KiB PostgreSQL JSONB datum size; no duplicate supplier targets or extra fields. No private supplier writes or central edits.
  - Returns the same selection fields for requested suppliers, sorted by UUID, not command order. Disabling an absent eligible supplier returns `enabled: false, revision: null` without inserting a row.
  - Null expected revision means absence. Existing revisions must match even for no-ops. No-op does not update timestamps/revision. Trigger-managed revision increments only on actual enabled-state change. Safe-integer revision range matches JavaScript. JSON command revisions must be numeric canonical integer tokens in 1–9007199254740991, not strings, decimal-scale values such as `1.0`, or fractions. Use validated JavaScript integers and `JSON.stringify`, which emits canonical integer tokens. PostgREST's typed bigint country argument has its own decoding boundary. Conflict SQLSTATE `40001` requires refetch/review, not blind retry with a new revision.
- `company_operating_country(p_company_account_id uuid) RETURNS jsonb`
- `set_company_operating_country(p_company_account_id uuid, p_country_code text, p_expected_revision bigint) RETURNS jsonb`
  - Both return exactly `companyAccountId`, `countryCode`, `revision`, validated by shared `parseCompanyOperatingCountry`. It rejects foreign/malformed UUIDs, extra fields, noncanonical countries, unsafe/noninteger revisions and a non-null country paired with null revision; results are detached and frozen. Unconfigured country and revision are null. Country setter uses CAS, does not manufacture a row for absent-to-null, and preserves revision for no-ops.

## Authorization, locking and errors

Revision representation validation examines PostgreSQL's normalized JSONB text, not the original wire token: exponent notation may already have normalized to an integer before these checks. Decimal scale retained by JSONB (for example `1.0`) is rejected. The 64 KiB limit is `pg_column_size` of the JSONB datum, not a byte-for-byte HTTP body limit; the 100-command limit is independently enforced.

All SECURITY DEFINER functions have empty fixed search paths and schema-qualified application relations/helpers. Internal helpers are not client-callable. Anonymous EXECUTE and PUBLIC EXECUTE are revoked. The pure country validator alone is executable by service_role so its new-table CHECK works during legitimate server writes.

Writes lock the company account, then recheck owner/membership authority and existing `is_company_account_writable`. Managers' qualifying memberships are SHARE-locked, preventing concurrent deactivation/demotion during a successful operation. Company locking serializes country CAS and RPC batches, including creation of absent relationships. Suppliers are SHARE-locked in UUID order to prevent concurrent lifecycle changes; existing relationship rows are UPDATE-locked before revision comparisons. Opposite input orders use the same supplier lock order. No SKIP LOCKED, partial success or swallowed errors.

Any failing command aborts all earlier writes in that RPC statement. Missing suppliers, unconfigured drafts, and all non-active enable attempts produce generic `22023 / Supplier unavailable`. Existing draft disable is permitted. Shape validation uses generic `22023`; authority/writability denial uses `42501`; stale revisions use `40001`. Messages do not interpolate names, account references, metadata or submitted commands. Typed PostgreSQL argument decoding is outside these function bodies.

## Direct privileges

The old authenticated INSERT/UPDATE policies bypass CAS and lifecycle checks. Drop those two policies and revoke all PUBLIC/anon/authenticated table privileges on company_suppliers, plus explicit SELECT/INSERT/UPDATE/REFERENCES column grants. Direct SELECT is also removed because the row contains private account/reference metadata. Keep RLS and the old SELECT policy as defense-in-depth. No current `src` or standalone `admin` code uses company_suppliers directly.

Preserve service_role table grants, existing triggers and Platform Admin server operation paths. Do not change company_product_overrides privileges/policies, product discovery, pricing, products, feeds, cost events or licensing. The new preferences table has default-deny RLS and no client table grants. Existing provider default grants, inherited-role access and unexpected policies must be inventoried before any future installation; effective-privilege SQL assertions must pass, not merely the source REVOKE check.

The sole helper exception is EXECUTE on the pure `scv22_country_valid(text)` predicate for service_role, because PostgreSQL evaluates the preferences CHECK constraint as the direct writer. Browser roles still cannot execute it; display, locking and trigger helpers remain sealed. This grant exposes no table data and changes no tenant authority.

The new preferences table resets service_role default table grants before granting SELECT/INSERT/UPDATE only, so ordinary service-role DELETE/TRUNCATE cannot reset revision history. Existing company_suppliers service-role privileges are unchanged. Custom inherited roles and migration-owner powers still require environment-specific verification.

## Country persistence

Use new `company_supplier_preferences`, keyed by the existing company UUID, with nullable `operating_country_code`, CAS revision and updated timestamp. This avoids broadening the existing company_accounts client-update surface or editing legacy company_settings. No backfill, default country, currency/address inference or supplier-selection trigger.

The explicit 249-code canonical allowlist is statically compared against SC-V2.1. Storage accepts uppercase canonical codes or SQL NULL; normalization/legacy suggestions require separate explicit confirmation by a future client. Lowercase, blanks, aliases and unassigned codes are rejected. Coverage must be one-dimensional, nonempty, <=249 entries and entirely canonical; otherwise return null, never worldwide. Deduplicate and sort valid coverage.

The `scv22_country_metadata` BEFORE INSERT/UPDATE trigger is SECURITY INVOKER with an empty search path. Insert initializes revision 1 and a clock timestamp. Every permitted UPDATE, including service_role, must supply transient `write_expected_revision` equal to the locked OLD revision; omitted/stale evidence or manually changing revision raises `40001`. The trigger consumes evidence back to NULL (also required by CHECK), increments once only for a changed country, and keeps timestamps strictly increasing even in one transaction. A no-op retains the previous revision and timestamp, ignoring attempted timestamp edits. Company identity is immutable. RPC updates set the evidence and country only; they do not increment metadata a second time. Direct server writers should additionally use a revision WHERE predicate and verify affected rows. An UPDATE matching zero rows is not an applied write. Trigger enforcement rejects stale evidence on a matched row, including after a concurrent writer; two-connection execution remains required to certify this behavior. Privileged users able to disable triggers remain outside the client security boundary.

## Subscriber name projection

`scv22_display_name` and shared `projectSubscriberSupplierName` never rename or persist central records. Replace C0, DEL and C1 controls with spaces; retain at most 200 UTF-16 units without splitting a Unicode codepoint; trim the explicit ECMAScript whitespace set; use `Unnamed supplier` if empty. No ellipsis or hidden original-name metadata is returned. This is codepoint-safe, not grapheme-cluster truncation. PostgreSQL UTF-8 text cannot contain NUL or lone surrogates; the JavaScript helper additionally replaces lone surrogates with U+FFFD, and strict transport validation rejects unpaired surrogates. No name-based directory exclusions remain. Long/control-bearing names cannot by themselves abort a company list or disable. Raw central names remain available only through existing Platform Admin paths. IDs/statuses are unchanged; invalid identities and unsafe stored revisions still fail closed.

## Validation and future acceptance

`tests/scv22-sql-static.test.ts` runs with existing Vitest dependencies and only reads source. It verifies country parity, function/search-path inventory, explicit helper/client grants, privilege removal and protected-table DML exclusion. It does not parse PL/pgSQL or certify database behavior.

`tests/scv22-central-supplier-security.sql` is a rollback-only disposable acceptance artifact, not an automatic test hook. It requires actual quote, invoice, job, company_presets, catalogue and settings tables with their source trigger dependencies, as well as Block 2B/2C and this migration. Missing tables or empty required fixture tables abort; there is no reduced-schema historical PASS. It inserts nonempty linked synthetic historical documents with commercial snapshots, saved designs and supplier IDs, plus catalogue/settings/cost history/override rows. Full-row fingerprints (including payload/state, revision and timestamps) are compared after enable, disable and reactivate, and at the end; original supplier names are separately compared. It never updates historical rows. The test-only temporary history assertion function is SECURITY DEFINER to read the snapshots while the caller uses the real authenticated role; it is not part of the migration or public application API.

The harness also covers long/control-bearing names, draft visibility/disable, direct/RPC country metadata/no-op/stale evidence, and calls the unchanged effective_company_supplier_products RPC after privilege revocation, enablement, disablement and reactivation, with foreign-tenant and cost/asset withholding assertions. The minimal existing supplier fixture uses synthetic Auth and writability. Successful future execution with that helper would not certify real provider Auth or real trial-expiry logic. Historical fixture setup must use the actual source schemas and latest constraints/triggers, not fabricated replacement tables. Historical Block 2B direct-SELECT expectations belong to its migration prefix, not the post-SC-V2.2 privilege model.

Before installation, separately authorize representative disposable PostgreSQL execution with the current real helper/trigger definitions, account trial-expiry and paid/read-only cases, real historical fixtures, function ownership/ACL checks and two-connection races (absent-row creation, stale update, membership demotion, supplier pause). Sequential rollback assertions do not prove concurrency. No PostgreSQL grammar parser/psql is available in the current checked tooling; do not label static assertions as SQL syntax certification.

## Compatibility and rollback

Requires the supplier foundation, effective projection and current account-writability helper. Install as a privileged migration owner able to bypass the underlying RLS; fail on any same-name function collision/overload rather than replace unrelated routines. The artifact uses an explicit transaction and is deliberately not replay-idempotent. No data deletion, destructive backfill or historical migration edit.

Pre-install review must check actual effective ACLs/column grants, schema ownership, revision trigger presence, and existing identities/revisions. Current Platform Admin may continue accepting long/control-bearing names: subscriber display projection now safely accommodates those future writes as well as legacy records without altering Platform Admin. Existing draft relationships remain identifiable but never newly enableable. Historical service-role company_suppliers revisions above JavaScript's safe-integer range still require explicit reconciliation; this migration does not rewrite them. The new country evidence column must remain NULL in stored rows and is excluded from every public response. Function-name collision checks/revokes include both new helpers. No additional SECURITY DEFINER functions are introduced by these corrections; installation ownership requirements remain unchanged.

Company row locking may contend with existing billing/account updates; preserve the established helper's writability semantics and assess lock ordering with server writers during the separately approved concurrency tests. No existing billing functions are changed.

Before execution, capture exact prior ACLs (including column grants), policy definitions, function ownership and schema/data fingerprints. A failed migration transaction rolls back. After installation, prefer forward repair or revoking the five new public RPC EXECUTEs to suspend management. Retain preferences/company relationships and hardened table privileges. Fully removing the new table requires a backup and explicit approval if countries have been saved. Restoring old authenticated DML policies/grants restores the bypass and is not a safe default rollback. Do not drop new functions while their CHECK depends on the country validator. No rollback is executed or automatically scheduled.
